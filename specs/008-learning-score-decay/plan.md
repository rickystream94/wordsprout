# Implementation Plan: Learning Score Decay

**Branch**: `feature/008-learning-score-decay` | **Date**: 2026-05-17 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `/specs/008-learning-score-decay/spec.md`

## Summary

Phrasebook entry learning scores currently remain at their peak value indefinitely after a review session. This feature introduces automatic progressive decay: after a 7-day grace period, scores decrease by 1 point every 3 days of inactivity. Decay is computed purely on the client (IndexedDB) at most once per calendar day, triggered by the existing app-load lifecycle. A new `decayBaseScore` field anchors the formula so it is idempotent across multiple devices — any device computing decay from the same `decayBaseScore` + `lastReviewedDate` produces the identical target score, making last-write-wins sync safe. No new infrastructure is required. Changed entries are synced to Cosmos DB via the existing `PUT /entries/:id` HTTP trigger and offline mutation queue.

## Technical Context

**Language/Version**: TypeScript 5.x
**Primary Dependencies**: Dexie.js 4.x (IndexedDB), React 18, `dexie-react-hooks`
**Storage**: IndexedDB (Dexie) as primary client-side store; Azure Cosmos DB Serverless as sync target
**Testing**: Vitest 4.x, `@testing-library/react` 16.x, jsdom
**Target Platform**: Progressive Web App (browsers, desktop + mobile)
**Project Type**: Web application (PWA frontend + Azure Functions API)
**Performance Goals**: Decay pass imperceptible to user — bulk IndexedDB update completes in <100ms for typical collection sizes (<500 entries)
**Constraints**: Offline-capable (decay works with no network); no new Azure infrastructure; at most one decay pass per calendar day per device; decay formula is idempotent across devices via `decayBaseScore` anchor field; no Dexie schema version bump needed; decay constants (`DECAY_GRACE_DAYS`, `DECAY_RATE_DAYS`) sourced from Vite env vars with safe production defaults
**Scale/Scope**: Single-user per device; personal vocabulary collections (typically 50–500 entries)

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

- ✅ **I. Encounter-First** — Decay only modifies scores on existing user-created entries. No vocabulary is added, suggested, or mandated by the app.
- ✅ **II. Learner Ownership** — Decay is an automated score adjustment, not content modification. Users can continue to edit or delete any entry at any time.
- ✅ **III. Offline-First** *(NON-NEGOTIABLE)* — Decay is computed from IndexedDB with no network dependency. Sync to Cosmos DB is enqueued and replayed when online, following existing patterns.
- ✅ **IV. AI as Assistant** — No AI calls involved in this feature.
- ✅ **V. Cost-Conscious** — Zero new infrastructure. Cosmos DB write RUs are proportional to the number of entries that actually decay (skipping entries with no score change). No new Azure services activated.

*Post-design re-check: All five gates still pass. No complexity tracking entries required.*
